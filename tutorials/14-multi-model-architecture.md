# 14. 多模型协作架构

## 🎯 本课目标

理解"根据不同任务选择不同模型"的设计思路，学会在实际使用中高效切换。

> ⏱️ **预计时间**：20-30 分钟
> 🧠 **重点**：理解"什么时候用什么模型"

---

## 🤔 为什么要协作？

你已经知道 Codex 擅长代码，Claude 擅长解释。但真实场景通常是混合的：

> "帮我看一下这段代码有没有 bug，如果有的话帮我修复。"

这个需求包含了两个环节：
1. **分析有没有 bug** → Claude 更擅长
2. **修复代码** → Codex 更擅长

一个模型从头做到尾也能完成，但两个模型分工，每个环节用最擅长的那一个，效果更好。

---

## 🏗️ 三层思维模型

```
┌─────────────────────────────────┐
│          你的任务                 │
├─────────────────────────────────┤
│    判断：这个任务属于什么类型？     │  ← 你来做判断
├─────────────────────────────────┤
│  Codex（写）    │  Claude（懂）   │  ← 在 CC-Switch 中切换
└─────────────────────────────────┘
```

你不需要写代码，不需要搭服务器。你只需要**在脑子里做一个判断**，然后在 CC-Switch 的模型列表中点一下切换。

---

## 🎯 任务分类指南

### 给 Codex 的任务

| 任务 | 示例 |
|------|------|
| 写新代码 | "写一个登录功能的 Python 代码" |
| 修 bug | "这段代码报错 TypeError，帮我修复" |
| 代码翻译 | "把这段 JS 翻译成 Python" |
| 写测试 | "给这个函数写单元测试" |
| 优化代码 | "这段代码太慢了，帮我优化" |
| 写正则表达式 | "写一个匹配邮箱的正则" |
| SQL 查询 | "写一个查询最近7天订单的SQL" |

### 给 Claude 的任务

| 任务 | 示例 |
|------|------|
| 解释代码 | "解释这段代码每一步在做什么" |
| 代码审查 | "帮我审查这段代码有什么问题" |
| 分析逻辑 | "分析这个算法的时间复杂度" |
| 写文档 | "给这个项目写 README" |
| 长文本总结 | "总结这篇技术文章的核心观点" |
| 复杂推理 | "分析为什么这个方案比那个好" |

### 不确定时怎么办？

两个都问！同一个问题分别发给 Codex 和 Claude，谁的答案更好用谁的。多一次 API 调用花不了多少钱，但能得到更好的结果。

## 📋 实战示例：完整的 debug 流程

假设你的代码报了一个看不懂的错误：

```
第 1 步：切换到 Claude
输入："我运行Python代码报了以下错误，帮我解释这是什么意思：
[粘贴完整错误信息]"
→ Claude 用大白话解释错误原因

第 2 步：切换到 Codex
输入："我的代码报了这个错误：[错误信息]
我的代码是：[粘贴代码]
请帮我修复"
→ Codex 给出修复后的代码

第 3 步：切回 Claude
输入："下面两段代码，修复前的和修复后的。请确认修复是正确的：
[原始代码]
[修复后代码]"
→ Claude 帮你做最终审查
```

整个过程你只做了三件事：**切换模型 → 输入问题 → 看答案**。

---

## 💡 进阶：建立"模型使用习惯"

用久了你会形成肌肉记忆：

| 看到任务 | 自动反应 |
|----------|---------|
| 看到代码需求 | 手自动切到 Codex |
| 看到报错信息 | 先用 Claude 分析，再切 Codex 修 |
| 看到长文章 | 切到 Claude |
| 看到"帮我写..." | 切到 Codex |
| 看到"帮我解释..." | 切到 Claude |

这就像用快捷键一样，不需要思考。

---

## 📊 单模型 vs 双模型

| 维度 | 只用 Codex | 只用 Claude | 双模型切换 |
|------|-----------|------------|-----------|
| 代码生成 | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐（用 Codex） |
| 解释分析 | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐（用 Claude） |
| 操作复杂度 | 简单 | 简单 | 多一步切换 |
| 整体效果 | 好 | 好 | 更好 |
